## Summary

ros.ai should become the open, local workspace where people direct AI agents and agents of any vendor do research, analysis and coding in the open. The canvas becomes a map with four jobs: the task board agents take work from, the shared memory every agent reads, the policy surface that bounds them, and the record people read afterwards. "Git for knowledge work" survives as the fourth job, not the product.

- **Problem.** Agents now do the work in the dark: each vendor in its own window, a hidden task list, no shared memory across vendors, no record of which source or decision a claim rests on, and guardrails the person never sees.
- **Solution.** One map, any harness (Claude Code through the Agent SDK, Codex, outside sessions over MCP, later ACP), rules enforced at ros.ai's own server where every vendor's calls meet, and every step kept with its source. Orchestration, semi-automatic research, coding, experiments and connectors are each a design on that map, built on code that exists.
- **Market.** No analyst names it yet. The direction moves ros.ai from research-tool budgets toward agent spend, where the categories are ten times larger and growing 22–50% a year; the research wedge alone has a bottom-up market of about $2.5B a year. Europe first, on the EU's May 2026 research-AI guidelines and Dutch DPIA friction.
- **Competitors.** The labs' command centres (Codex app, Claude Code Agent Teams, Antigravity, VS Code Agent Sessions) have the shape and the users but keep the state hidden and single-vendor. AIPOCH and Jupyter AI are open and neutral but have no map. Nobody holds the top-right corner: any vendor's agents on a map the person sees. There is no moat today, only that position and a window.
- **Business.** Free MIT local app; a paid team tier at $20–30 a seat and an organisation server from about EUR 15,000 a year for SSO, audit, one policy set and hosting. n8n is the comparable, and Accel led it.
- **Product-market fit.** None yet: zero users, no installer, agent features verified against stand-ins. The 90-day proof is 50 weekly-active installs, three signed pilots, and five users who pass the morning test: they set the evening's agent work in ros.ai and decide from the queue in the morning. The first build step is two agents at once with lanes and the attention queue.

**Open decision for Adam:** adopt this direction, then pick the next piece of work, a detailed plan for step one or a rewrite of the application draft around "Run your agents in the open".

## Product overview

ros.ai is an open-source local workspace where a person directs AI agents from any vendor, and the agents do research, analysis and coding in the open on one map the person owns. Today it is a single-agent research workbench with careful provenance and safety. The October 2026 direction turns the same canvas into the place agents work from, not the place they report to.

**What exists today (main, 16 October 2026).** One command serves a browser canvas on the person's own machine. The canvas holds blocks (notes, Search, Finding, Code, Notebook, Dataset, Figure, Report and Agent) inside Groups the person draws. A Claude Code turn, run through the Agent SDK with the person's own API key, or a Codex turn works through tools that can only propose: fan out web searches, read pages, write Findings whose quotes must match the page word for word, group by theme, draft a report. Every step lands as a block to inspect, accept or undo.

- Python runs only in a Docker sandbox, and projects are plain files in a folder the person picks.
- Spend is capped per model connection, and credentials stay on the server side.
- An MCP server lets the person's own Claude Code or Codex work on the same canvas with its own login.
- Connectors for Drive, Zotero, Notion, GitHub, Slack and Tavily hold credentials; using them from the canvas is not built yet.
- MIT licence, one founder, about four weeks of work with agents. No users, no installer, no CI.

**What the direction makes it.** The canvas becomes a living map that agents work in. It has four jobs, and the earlier "git for knowledge work" idea survives as the fourth:

| Job of the map | For whom | What it replaces today |
| --- | --- | --- |
| Task board: goals broken into Task nodes with status, budget and acceptance checks, claimed by agents | Agents and the person | Claude Code Agent Teams' shared task list and mailbox; Codex app threads; a lab's private orchestration |
| Shared memory: the question, decisions, sources, findings and rules, read by every agent before it acts | Agents | Kosmos's world model; Karpathy's program.md; CLAUDE.md and AGENTS.md files |
| Policy surface: permissions, budgets, network and rules on Groups, enforced where the tool calls pass | The person and the organisation | Invisible API guardrails; per-vendor permission prompts |
| Record: what was done, from which sources, decided by whom | People, reviewers, auditors, the next agent | Transcripts nobody reads; "git for knowledge work" |

ros.ai runs harnesses, not models: Claude Code through the Agent SDK, Codex through its app server, outside sessions over MCP, later Gemini CLI and OpenCode over one ACP adapter, local models through OpenAI-compatible connections, and deterministic tools as agents with no model. It is not a pipeline builder, not a hosted service and not a model vendor.

*Figure 1 (diagram in the doc): Agents of any vendor work one map; every call passes ros.ai's checks.* On the left, the person sets the goal, the rules and the budget, approves the plan and decides from the attention queue; the organisation holds the policy set, the audit record and the shared map. In the centre, the map's four jobs: the task board (Task nodes with acceptance check, budget and owner; lanes per agent), the shared memory (question, decisions, sources, findings and rules, read each step), the policy surface (permissions, budgets, network, rules drawn on Groups) and the record (what was done, which sources, decided by whom). On the right, the harnesses: Claude Code (Agent SDK, API key), Codex (its own app server), outside sessions (over the MCP server), other harnesses (over ACP, later), local models (OpenAI-compatible) and tools with no model (a search, a script). Every agent's calls pass one set of checks before they reach the map, enforced by ros.ai's server whatever the vendor: the Docker sandbox, the budget per connection, the network allowance, the approval modes, quotes that must match the page, outward writes that ask first, and spend shown per lane.

The person sets the work and decides, agents of any vendor claim tasks and write nodes, and every call passes the same checks, which is why the rules hold across vendors.

## Problem

Agents now do much of the work in research, analysis and coding, and they do it in the dark. Each vendor's agents run in their own window with a hidden task list, no shared memory across vendors, no record of which source or decision a claim rests on, and guardrails the person never sees. The person's job has moved from doing the work to directing, bounding and deciding, and no tool is built for that job across vendors.

Five things break once more than one agent works on one piece of work:

- **Direction.** Goals, rules and budgets live in prompts and per-vendor settings, re-typed for every agent and every session. Claude Code's Agent Teams inherit CLAUDE.md and MCP servers but not conversation history.
- **Memory.** Each harness keeps its own context, and hand-offs lose it. The person cannot see what one agent told the next.
- **Trust.** Output arrives without its path. Autonomous research systems are right most of the time and wrong often enough that every result needs a human check, and the checker gets no instrument.
- **Control.** Guardrails are API filters the person neither sees nor shapes, and none spans vendors. Cost is the first limit buyers name, and spend per agent is invisible.
- **Record.** What was done, from which sources, decided by whom, exists nowhere a reviewer, an auditor or the next agent can read.

Who feels it first: researchers and analysts who already run several agents on work that lasts days, and the organisations that must stand behind the result. Researchers sit where the pain is sharpest, because the EU now asks them to keep prompts, outputs and decisions, and because most of them will not put their data into a vendor's cloud.

## Solution

ros.ai answers the problem with one map that agents work in and people direct. The person writes the goal, the rules and the budget. Agents of any vendor take tasks from the map, work in parallel in their own lanes and sandboxes, and leave every step, source and decision on it. The person sees only the agents that need them, and decides.

The six capabilities Adam named are each a design on the map, built on code that exists:

| Capability | Design on the map | On main today | What the direction adds |
| --- | --- | --- | --- |
| Orchestration | Goals become Task nodes with an acceptance check, budget and owner. Agents claim tasks and work in lanes. Hand-offs carry an explicit context packet. Lead and Reviewer are Agent nodes, not code. | One assistant turn at a time, at most two searches in parallel, one Agent node per run, proposals that wait for approval. | Two or more agents at once, lanes, the attention queue, Task nodes, and any harness: Agent SDK, Codex app server, MCP sessions, later ACP. |
| Semi-automatic research | The program (question, rules, acceptance checks, hypotheses) sits on the map. The loop runs today's Actions. The ratchet keeps what improves and shows what was reverted. Checkpoints are the approval modes. | Fan-out search, page reading, Findings with verified quotes, Decide and group, report draft, run by one agent per turn. | Hypothesis and Experiment nodes with status and metric, keep-or-revert, and overnight mode under a budget. |
| Coding and experiments | Code and Notebook are the agents' playground with every attempt kept. A code task gets a branch of the project folder, and accepting is a merge. | Docker-sandboxed Code and Notebook nodes, hashed artifacts, an attempts appendix in exports. | Agents that run, read the error and retry inside a node; Experiment nodes with a metric; a branch per task. |
| Third-party tools | Connector nodes in both directions. Every outward write asks first. ros.ai is both an MCP client and an MCP server. | Plugins hold credentials for Drive, Zotero, Notion, GitHub, Slack and Tavily; the MCP server exposes ros\_\* tools to outside agents. | Connectors used from the canvas: Zotero in, Google Docs and GitHub out with a separate write grant; any MCP server as a tool. |
| Path, sources and decisions in one conversation | A branch map beside the chat. Click a sentence to light up its source. Mark a source wrong and every dependent finding is flagged. Decisions land in a ledger every agent reads. | Steps as nodes, quotes verified against pages, decisions as a field on nodes, undo that never deletes evidence. | Project-level Decision nodes, source invalidation across lanes, redo from here, and what changed my answer. |
| Many agents with guardrails and context | Every agent reads the map, not a transcript. Deterministic checks run at ros.ai's server, rules derive from decisions, a Reviewer agent covers the rest, and every block shows the checks it passed. | Sandbox, per-connection budget, approval modes, quote matching and server-side credentials, all enforced today but not shown. | Checks shown on blocks, rules drawn on Groups, contradiction edges between lanes, a Reviewer with evidence tools only. |

Why the guardrails hold across vendors: every tool call and every output passes through ros.ai's own server. The sandbox, the budget, the network allowance, the quote check and the outward-write prompt therefore apply to a Claude Code lane, a Codex lane and a local model alike. A vendor cannot enforce a rule across another vendor's agent. ros.ai can, because it is where the calls meet.

What it is not: a pipeline builder, a model or a hosted service. n8n, Dify and Langflow draw a fixed flow that developers run many times. ros.ai's map grows with one piece of work that is never the same twice.

The demo that shows the difference: at six in the evening the person writes a question, three rules and a budget. Three lanes work overnight, one on literature, one on data in a Notebook, one on a chart in Code. At nine the queue says four decisions are waiting. Behind it the map shows what was done, which source each finding rests on, one contradiction between two lanes, and the spend. The person decides, and the report draft updates.

## Business value

The value of running agents in the open is more delegated work per person, less spend per result, fewer claims nobody can check, and assets that compound with use. None of it is measured yet; the proof plan under Product-market fit defines the first measurements.

| Who | What they gain | How it would show |
| --- | --- | --- |
| A researcher or analyst with one agent | The question, rules and budget are set once and read by every turn. Context survives across sessions and tools. Every claim carries a page that was read, and nothing is deleted. | Hours of re-briefing removed; share of claims with a source; time from question to a reviewed draft |
| A group running several agents | Lanes, the attention queue and hand-off packets mean the person reviews four decisions, not four transcripts. Contradictions are drawn when they arise, not found in the final text. Spend is visible per lane and capped. | Decisions handled per person per day; spend per accepted finding; contradictions caught before the draft |
| An organisation that must stand behind the work | One policy set enforced across every vendor's agent. The audit record (what was done, from which sources, decided by whom) comes out as a by-product, in the form the EU guidelines and publishers ask for. Data stays on the machine, so the DPIA is the institution's own. | Time to approve a new agent or tool; audit preparation time; vendors under one policy |
| Anyone switching models or harnesses | The map, the program and the rules stay when the engine changes, so a new model or a new vendor costs a lane, not a migration. | Harnesses in use per project; cost of a vendor switch |

**Cost is the first-order argument.** Multi-agent runs use about 15 times the tokens of a chat, and about a fifth of organisations already say token and operating costs constrain their use (sources under The market). ros.ai reserves a budget per turn and caps spend per connection today. Showing and capping spend per lane is how buyers will judge agent work, and it is the part of the direction closest to shipped code.

**Why the value rises with better models.** Better models run longer alone and take more decisions per person per day. The person's work shifts from doing to directing, bounding and deciding, which is the surface ros.ai is. Labs sell engines; ros.ai sells the cockpit, and a faster engine makes the cockpit matter more. Each new AI product is another engine for the same cockpit, because it arrives as a lane or a connector over MCP or ACP.

**Assets that compound.** Four things grow with use and are why a team stays. None exists on day one.

1. The project map: decisions, rules, sources and the team's approval history. A rival starts at zero with every team.
2. The library of programs: research loops, experiment recipes and review checks kept as graph templates and SKILL.md files, portable and sharable.
3. The organisation's policy set and audit record, which is what the paid server hosts.
4. Context across tools that no single vendor holds, because the connectors bring it to one map.

## Competitor analysis

No product today combines local, open, any vendor's harness, a map that is both task board and shared memory, rules enforced where the calls meet, and provenance per step. The nearest threats are the labs' own command centres growing a visible map, and the open science agents adding a canvas.

**What the direction changes in the picture.** The earlier positioning competed with research workbenches and literature tools. The task-board framing adds three groups that were not rivals before: the vendor command centres, the pipeline builders and the agent-operations tools. It also changes the sharpest rival. It is no longer AIPOCH but Claude Code Agent Teams and the Codex app, because they already have the shape every credible multi-agent system converges on (parallel agents, one shared state, a human gate) and they have the users. What they keep hidden, single-vendor and text-only is exactly what ros.ai puts on a map.

**Where ros.ai is different.** Five properties, together: local with projects as plain files and no account; MIT; any vendor's harness through the Agent SDK, the Codex app server, MCP and later ACP; a map that is the task board, the shared memory, the policy surface and the record; and checks enforced at ros.ai's own server, where every vendor's calls meet. Each rival has at most three of the five. One precision matters when claiming bring-your-own-agent: Anthropic restricted consumer subscription sign-in to its own apps in 2026 and sells Agent SDK credits for programmatic use ([falcao.org, personal blog](https://falcao.org/posts/anthropic-claude-access-crackdown-ecosystem-fallout/)). ros.ai uses the Agent SDK with the person's API key and lets Codex own its own login; it never proxies subscription tokens, which AIPOCH's isolated sign-in route does.

**The honest statement.** There is no moat today. There is a position (local, open, neutral, graph-shaped, enforcing) and a window before the labs generalise their command centres beyond code and before Microsoft adds an agent manager to Office. Three events would close the window: a lab opens its command centre to rivals' agents and draws the task list as a map; AIPOCH adds a canvas with lanes; Jupyter AI's ACP multi-agent spreads through universities before ros.ai has users there. The answer to all three is the same: be in the daily loop of people who run several agents on long work before it happens, starting with researchers.

## Business model

The local app is free and open forever. Organisations pay for a hosted or self-hosted server that holds the shared map, the policy set, single sign-on, audit exports and the program library. This is the pattern that pays in open source, and Accel has funded it twice in Europe (n8n, Polars). The sale is not a record and not swarms. It is: run your agents here, from any vendor, within your rules, and keep what they did.

| Tier | What it includes | Price anchor | Who buys |
| --- | --- | --- | --- |
| Local app (MIT) | The whole product: canvas, agents of any vendor on the person's own keys, sandbox, provenance, MCP server, connectors | Free forever; model spend stays on the person's own key | Individuals, labs, students |
| Team, hosted or single-tenant | Shared map for a group, roles, shared program library, backups, policy defaults | $20–30 per seat per month, the band of Overleaf group, Notion Business, Claude Team and Cursor Teams; 40% academic discount, the Overleaf precedent | Research groups, consultancy and analyst teams |
| Organisation server, self-hosted or single-tenant | SAML or SURFconext sign-on, SCIM, an audit log of agent actions and exports, one policy set enforced on every lane, a DPIA pack and an Article 28 processing agreement, support | Quote from about EUR 15,000 a year, inside 2i2c's General Member band and below Consensus's enterprise median of $45,750 | Faculties, institutes, legal, compliance and due-diligence teams |
| Later and uncertain | A marketplace of programs and review checks | Revenue share | Program authors and their users |

Worked examples: a lab of 25 at $25 a seat is $7,500 a year; a faculty of 100 is $30,000 a year. Both stay under the EUR 216,000 EU tender threshold, so a faculty pilot can be contracted directly. Price anchors and precedents are sourced in the Accel notes and listed under Sources.

**Three rules.** Do not bundle inference: model spend stays on the user's or the institution's key, which keeps the seat price procurement-friendly and avoids the margin squeeze Cursor reports on individual accounts. Keep MIT for the core and gate organisation features, not the licence: Elastic, Redis and HashiCorp each triggered a foundation fork when they relicensed and later softened, while the fastest-growing open companies gate SSO, audit and hosting. Never proxy a vendor's subscription token; the Agent SDK with an API key and Codex's own sign-in are the sanctioned routes.

**Precedents with numbers.** n8n had about $40M in annual revenue at its Accel-led Series C in October 2025 and about $100M by April 2026, with roughly 55% from cloud, 30% from enterprise self-hosted licences and 15% embedded ([Sacra](https://sacra.com/c/n8n/); [ValueAdd VC, secondary](https://valueaddvc.com/blog/n8n-valuation-2026-5-2b-40m-arr-and-how-it-compares-to-zapier-and-make)). Supabase reached about $170M in annual revenue and a $10.5B valuation ([Sacra](https://sacra.com/c/supabase/)); PostHog was cash-flow positive at a $920M valuation ([Crunchbase News](https://news.crunchbase.com/ai/startup-posthog-tweet-funding-round-stripe)); GitLab reported $955M of revenue for fiscal 2026 ([SEC filing](https://www.sec.gov/Archives/edgar/data/1653482/000162828026013795/gitlab-ex99120260131fy26.htm)). Free-to-paid conversion in open-source software is typically 0.5–3% of active users (aggregator estimate, [Monetizely](https://www.getmonetizely.com/articles/whats-the-optimal-conversion-rate-from-free-to-paid-in-open-source-saas)), so the plan should count departmental deals of $10,000–50,000 a year, not individual subscriptions. Cline is the model-cost precedent: open core, the user's own API keys, Teams at $20 a seat ([Sacra](https://sacra.com/c/cline)).

**Go-to-market, in the order the evidence supports.** First, bottom-up installs: a public one-command install, AISO workshops with students and early-career researchers, measured in weekly-active installs. Second, department-sponsored pilots with before-and-after numbers on the Overleaf and Cambridge model, championed by research IT, data stewards and integrity officers. Third, non-academic revenue from teams that run agents on work they must stand behind: consultancies and due-diligence teams, policy and public-sector analysts, legal and compliance teams, corporate R&D. The direction moves this third group forward: a team that already runs Claude Code and Codex on client work is a buyer for the organisation server from the first version that runs two agents at once, without waiting for the research wedge to mature. Research stays the first proving ground because the provenance pain is sharpest there, the EU guidelines create demand, and Adam has access at UvA; it is the design-partner market, not the revenue plan.

## Product-market fit

There is no product-market fit evidence yet, only a position and a plan. ros.ai has zero users beyond the founder, no installer and no CI, and its agent features were last verified against stand-in services. The direction sharpens what to prove: that people open ros.ai at nine in the morning to set the day's agent work, and that the agents run from it. If they open an agent and look at ros.ai afterwards, ros.ai is a feature.

**The archetype to name.** In Sequoia's terms this is a Hard Fact market ([Sequoia](https://sequoiacap.com/article/pmf-framework)): researchers and analysts accept scattered chats, notebooks and terminals as normal, so the market must be shown the alternative before it buys. Demand is nonetheless visible bottom-up. Radboud reports staff buying their own ChatGPT licences ([Radboud, Mar 2026](https://www.ru.nl/over-ons/nieuws/copilot-chat-verbeterd-door-toegang-tot-actuele-webinformatie)); Princeton built an AI Sandbox because faculty asked for a vetted environment ([Princeton](https://ai.princeton.edu/news/2025/princeton-ai-sandbox-provides-secure-environment-campus-researchers-use-llms)); at UvA medical informatics more than 90% of students use ChatGPT and privacy of input is the top ethical concern ([Frontiers in Education](https://www.frontiersin.org/journals/education/articles/10.3389/feduc.2025.1658415/full)). The institution's problem is governance, not enthusiasm.

**The bar, and where ros.ai stands.** Seed investors in developer and research tools treat stars as vanity and ask for weekly-active users, retention and named design partners ([Causo Hub](https://hub.causo.ai/guides/raising-seed-devtools-startup-2026); [Superhuman](https://blog.superhuman.com/how-superhuman-built-an-engine-to-find-product-market-fit/)).

| --- | --- | --- | --- |

**Build order on today's code.** The spine is the loop running with more than one agent under the person's rules. Everything else attaches to it.

1. Two agents at once, with lanes and the attention queue, using the existing per-turn budget reservation and concurrency limit as the hooks.
2. Task nodes and the program: goal, acceptance check, budget and owner, proposed by a Lead the way the fan-out plan is proposed today.
3. The ratchet: Hypothesis status and Experiment nodes with a metric, attempts and keep-or-revert, in the Docker sandbox that exists; overnight mode is Full access plus a budget plus the queue.
4. The ledger and one visible rule: project-level Decision nodes fed to every turn, dependents flagged on change, and the check that every claim cites a read page shown on each block.
5. Outside agents work on the map: the MCP server records a Claude Code or Codex session's plan, sources and decisions as nodes, plus one ACP adapter for Gemini CLI and OpenCode.
6. Connectors in both directions: Zotero in, Google Docs out with a separate write grant, GitHub for code lanes.
7. Install and users: the one-command install from the roadmap, CI, then five to ten UvA researchers on real projects.

**What would make this wrong.**

- The labs generalise first and open their command centres to rivals' agents. Then neutrality weakens and ros.ai must win on the map and the rules; local, open and a head start with users are the defence.
- Multi-agent work stays niche. Agent adoption is in the single digits per department, and the Agent Teams write-up warns that activity does not equal value. The map must be useful with one agent, which the program, the ratchet and the ledger are; many agents only make it necessary.
- People stop caring about provenance once agents are reliable. The map is about directing and deciding, not only checking.
- Scope: six capabilities is a company, not a pull request. The build order picks one spine.
- One founder working with agents, and no standard set by one founder. Keep the graph format open and MCP-writable, do not bet on its adoption, and make the first hire packaging, CI and platforms.

**The open decision.** Adopt this direction as the one ros.ai builds toward, which changes the pitch line, the build order and the first buyers, and pick the next piece of work: a detailed plan for step one (two agents at once with lanes and the queue) or a rewrite of the application draft around "Run your agents in the open".
